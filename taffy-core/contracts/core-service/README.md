# Core Service contract

This contract connects a profile-owned browser manager to the sandboxed Rust
core process. Commands mutate ordered reducer state; effects request bounded
asynchronous work from browser brokers; exactly one result returns for each
effect. Every message is generation-, revision-, deadline-, and idempotency-
bound.

The service receives no ambient browser, network, credential, filesystem, or
profile-directory authority.

`ReportBackupRestoreStageVerified` carries the complete bounded set of
selected `SkillRecord` values read back from the isolated native stage. Core
matches their identities, revisions and provenance against its retained plan
and runs the normal bootstrap catalogue validator before issuing commit
authority. Validation installs nothing, changes no source catalogue, restores
no run history and starts no target Core. Recovery keys, paths and other
backup record payloads do not enter this request.

`golden/backup-restore-stage-procedures.json` exercises the wire shape only;
its short definition bytes are deliberately not an admitted procedure.
Portable tests use the production procedure encoder and decoder to check
full admission. A structurally valid request is never itself commit authority.

Account HTTP remains a browser-broker responsibility with build-owned fixed
origins and routes. After a consequential token request has completed with a
bounded 2xx body, the browser passes that body once to
`ValidateAccountTokenResponse` for transient parsing and validation on the
sandboxed Rust sequence. The raw body and token bytes never enter reducer
state, the journal, UI contracts, logs, or tool workers; validated tokens
return only to the browser broker for immediate rotation into the
profile-owned secure store. A validator disconnect, timeout, malformed body,
or stale generation settles the dispatched operation as `OUTCOME_UNKNOWN`.

`ToolJobEffect` carries a task owner and the task binding embeds the complete
job only for the registered Python surface. The browser validates the nested
task, job and runtime identities before dispatch and task revocation cancels
the exact worker through the profile tool supervisor. Other runtime families
remain non-emitting and receive one correlated unavailable terminal.

## The persisted transaction layout

`schema/task_transaction.json` is the on-device journal format, and it is the
one place in this repository where a wire change reaches bytes a user's phone
already holds. Contiguous ordinals do not protect it: a field inserted in the
middle of a record renumbers everything after it, satisfies the contiguity rule,
and leaves every existing journal decoding into the wrong fields.

`schema/wire-ledger.json` records each ordinal once. Reordering, reuse,
retyping and removal are refused outright; an append needs `--refreeze`, which
needs the contract version raised, and an append inside a record the codec reads
also needs the codec's own `schema_version` raised, because that number is the
only thing an older decoder can use to tell the two layouts apart.

`golden/task-transaction.json` and `golden/task-transaction-v14.hex` are the
representative batch and its frozen bytes. They are an input to the generator
and a compiled-in fixture of `core-service-types`, which decodes and re-encodes
them on every `cargo test`. `schema/wire-ledger.json` names the same `.hex` file
as the frozen payload, so the name in this paragraph moves with every codec
`schema_version` bump and is checked by the generator rather than by a reader.

`golden/task-transaction-v6.hex`, `golden/task-transaction-v7.hex`,
`golden/task-transaction-v9.hex`, `golden/task-transaction-v10.hex`,
`golden/task-transaction-v11.hex`, `golden/task-transaction-v12.hex`,
`golden/task-transaction-v13.hex`, `golden/task-transaction-v27.hex`,
`golden/task-transaction-v28.hex` and `golden/task-transaction-v29.hex` are the
superseded layouts' frozen batches —
one file per version this codec has ever written. Version 8 has no file: its
bytes were never frozen before the version-9 bump reused the frozen-payload
file in place, and a superseded layout cannot be produced again. The gap is
recorded here rather than papered over with regenerated bytes that would
carry today's layout under yesterday's number. They stay because they cannot be produced again once the layout has
moved, and they stay under test: `core-service-types` asserts that this build
refuses each of them on its version, which is what decision
`docs/decisions/0058-the-journal-reads-every-version-it-has-written.md`
describes as today's behaviour rather than the behaviour it asks for. When the
supported version becomes a set, those assertions become decodes and these
files are what prove it. Note what version 7 shows about the cost: its members
were only *appended*, so nothing already written moved, and it is refused all
the same — a reader cannot tell a version-7 file that happens to contain no
handover from one truncated before it, and guessing is what the refusal exists
to prevent.
